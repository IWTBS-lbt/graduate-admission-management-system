## 1. 项目概述

### 1.1  项目名称

**研究生招生信息管理系统**（Graduate Admission Information Management System）

### 1.2  项目目标

构建一个覆盖研究生招生全流程的信息管理系统，实现从考生报名、初试复试管理、到录取统计分析的完整业务闭环，为招生人员提供高效的数据管理工具和决策分析支撑。

## 2. 需求分析

### 2.1  业务流程

研究生招生管理工作分为三个核心阶段：

```
第一阶段：考生报名
  考生填写报名表（个人简历 + 报考信息）
  → 招生人员录入系统
  → 形成考生档案

第二阶段：初试与复试
  初试 → 录入各科成绩 → 设定分数线 → 筛选复试名单
  → 复试 → 录入复试成绩
  → 公布录取分数线 → 判定录取

第三阶段：录取统计
  录取名单确定 → 统计分析
  → 年龄/来源/专业分布
  → 计划招生 vs 实际招生对比
```

### 2.2  功能需求

| 编号 | 功能模块 | 功能描述 | 优先级 |
|------|---------|---------|--------|
| F01 | 专业字典管理 | 专业的增删查改，维护计划内/外招生数 | P0 |
| F02 | 考生档案管理 | 考生个人信息与报考信息的录入、查询、修改、删除 | P0 |
| F03 | 初试成绩管理 | 政治、外语、专业基础三科成绩的录入与更新 | P0 |
| F04 | 复试资格筛选 | 根据单科线 + 总分线自动筛选进入复试的考生 | P1 |
| F05 | 复试成绩管理 | 复试专业科目、面试、上机成绩的录入与更新 | P1 |
| F06 | 录取名单生成 | 根据录取总分线自动判定并生成录取名单 | P1 |
| F07 | 各科成绩统计 | 政治/外语/专业基础的平均分、及格率、不及格率 | P2 |
| F08 | 分数段统计 | 按总分区间统计考生人数分布 | P2 |
| F09 | 录取生源分析 | 录取考生的年龄/来源/专业分布统计 | P2 |
| F10 | 计划与实招对比 | 各专业计划招生数与实际录取数对比 | P2 |

### 2.3  非功能需求

| 类别 | 要求 | 实现方式 |
|------|------|---------|
| 可用性 | 7×24 小时可用 | Spring Boot 内嵌 Tomcat，单点部署 |
| 性能 | 页面响应 < 2s | MyBatis-Plus 轻量 ORM + 数据库连接池 |
| 数据一致性 | 事务 ACID | `@Transactional` + InnoDB 外键约束 |
| 可维护性 | 分层架构，代码规范 | Controller → Service → Mapper 三层分离 |
| 可扩展性 | 模块化设计 | 新增功能模块只需添加新的 Controller/Service/Mapper |

### 3.2  分层职责

| 层次 | 包路径 | 职责 | 关键注解 |
|------|--------|------|---------|
| **Controller** | `com.admission.controller` | 接收 HTTP 请求，参数校验，调用 Service，返回统一 Result | `@RestController` `@RequestMapping` `@CrossOrigin` |
| **Service** | `com.admission.service` | 业务逻辑：事务管理、外键校验、筛选/录取算法、统计计算 | `@Service` `@Transactional` |
| **Mapper** | `com.admission.mapper` | 数据库访问：基础 CRUD（通过 BaseMapper）+ 手写 SQL | `@Mapper` `@Select` |
| **Entity** | `com.admission.entity` | 数据库表映射 | `@Data` `@TableName` `@TableId` |
| **VO** | `com.admission.vo` | 数据传输对象：跨表查询结果封装 | `@Data` |
| **Common** | `com.admission.common` | 通用组件：统一响应类 `Result` | `@Data` |

### 4.2  选 MyBatis-Plus 而非原生 MyBatis 的原因

| 对比维度 | 原生 MyBatis | MyBatis-Plus |
|---------|-------------|--------------|
| 基础 CRUD | 需手写 XML SQL | `BaseMapper<T>` 自动提供 |
| 条件构造 | 需手写 `<where>` 动态 SQL | LambdaQueryWrapper 链式调用 |
| 主键策略 | 手动指定 | `@TableId` 注解统一管理 |
| 分页 | 需引入 PageHelper | 内置分页插件 |
| 驼峰映射 | 需手动配置 `<resultMap>` | 一行配置 `map-underscore-to-camel-case=true` |

### 5.2  核心业务逻辑详解

#### 5.2.1  删除专业 — 外键完整性检查

```
流程：
  ① 前端发起 DELETE /major/delete/{majorCode}
  ② Controller 接收 majorCode，调用 Service
  ③ Service 查询 student 表：SELECT COUNT(*) FROM student WHERE major_code = ?
  ④ 如果 count > 0 → 抛出 RuntimeException("该专业下还有考生，无法删除！")
  ⑤ 如果 count = 0 → 调用 baseMapper.deleteById(majorCode)
  ⑥ 整个过程由 @Transactional 保证原子性
```

#### 5.2.2  复试资格筛选 — 多维度分数线

```
输入：politicsLine（政治线）、englishLine（外语线）、
      professionalBaseLine（专业基础线）、totalScoreLine（总分线）

SQL 逻辑：
  SELECT s.*, f.*
  FROM student s JOIN first_score f
  WHERE f.politics >= politicsLine
    AND f.english >= englishLine
    AND f.professional_base >= professionalBaseLine
    AND f.total >= totalScoreLine

筛选规则：所有条件必须同时满足（AND 关系），
         任一科目不达线或总分不达线均不能进入复试
```

#### 5.2.3  录取名单生成 — 总分排名判定

```
流程：
  ① 前端发起 POST /admission/generate?totalScoreLine=360
  ② Service 查询所有已有 first_score + second_score 的考生
  ③ 计算每位考生总成绩 = first_score.total + second_score.total
  ④ 筛选 total >= totalScoreLine 的考生
  ⑤ 清空旧的 admission 表数据
  ⑥ 批量插入新的录取名单（is_admitted=1，department="待定"）
  ⑦ 整个过程由 @Transactional(rollbackFor = Exception.class) 保证原子性
```

#### 5.2.4  统计分析 — 多维度数据聚合

```
各科成绩统计（GET /stats/subject）：
  对 politics / english / professional_base 分别计算：
  - 平均分（AVG）
  - 及格人数（score >= 60）
  - 不及格人数（score < 60）
  - 及格率 = 及格人数 / 总人数 × 100%

分数段统计（GET /stats/segment）：
  按总分划分为 5 段：
  [0,200)、[200,300)、[300,400)、[400,500)、[500,+∞)
  使用 CASE WHEN 分组 + COUNT 统计

录取生源分析（GET /stats/admission）：
  JOIN student + admission（WHERE is_admitted=1）
  按年龄/来源/专业三个维度 GROUP BY 统计
```

## 7. 数据库设计概要

> 详细设计请参见 [数据库设计报告](./数据库设计报告.md)

### 7.1  核心表

| 表名 | 主键 | 记录数（估） | 说明 |
|------|------|-------------|------|
| `major` | major_code | 50 | 专业字典 |
| `student` | exam_id | 10,000 | 考生档案 |
| `first_score` | exam_id | 10,000 | 初试成绩（含计算列 total） |
| `second_score` | exam_id | 3,000 | 复试成绩（含计算列 total） |
| `admission` | exam_id | 1,500 | 录取名单 |

### 7.2  关系图

```
major ──1:N──> student ──1:1──> first_score
                   │
                   ├──1:1──> second_score
                   │
                   └──1:1──> admission
```

### 7.3  关键设计点

- 使用 MySQL **GENERATED ALWAYS AS ... STORED** 计算列自动汇总各科总分，避免应用层计算误差
- 使用 **TINYINT(1)** 替代布尔类型（`is_fresh`、`is_admitted`），兼容 MySQL 所有版本
- 所有表使用 **InnoDB** 引擎，支持事务和外键约束
- 字符集统一使用 **utf8mb4**，支持全 Unicode

## 10. 安全设计

### 10.1  当前阶段

| 措施 | 实现方式 | 说明 |
|------|---------|------|
| SQL 注入防护 | MyBatis-Plus `#{}` 参数化查询 | 占位符方式，天然防注入 |
| 外键约束 | 数据库 FOREIGN KEY + 应用层 Service 校验 | 双重保障数据完整性 |
| 事务管理 | `@Transactional` | 保证关键操作的原子性 |
| 统一异常处理 | Controller try-catch → Result.fail() | 避免堆栈信息泄露到前端 |
| 跨域控制 | `@CrossOrigin(origins = "*")` | 开发阶段允许所有来源 |

### 10.2  后续增强建议

| 措施 | 优先级 | 说明 |
|------|--------|------|
| Spring Security / Shiro 权限框架 | 高 | 实现角色权限控制（管理员 vs 招生人员） |
| JWT Token 认证 | 高 | 替换当前简单的用户名密码登录 |
| CORS 白名单 | 中 | 生产环境限制允许的域名 |
| 接口限流 | 低 | 防止恶意高频调用 |
| 操作日志 | 低 | 记录关键操作审计轨迹 |

## 附录 B：关键技术问题与解决方案

| # | 问题 | 原因 | 解决方案 |
|---|------|------|---------|
| 1 | MySQL 不支持 BOOLEAN | 原生无此类型 | 使用 `TINYINT(1)` 替代（0/1） |
| 2 | 总分手动计算易出错 | 应用层计算 + 手动录入不一致 | 使用 `GENERATED ALWAYS AS ... STORED` 数据库计算列 |
| 3 | Spring Bean 找不到 | ServiceImpl 缺少 `@Service` 注解 | 为所有 ServiceImpl 添加 `@Service` |
| 4 | Lombok 编译报错 | IDEA 未开启注解处理器 | 开启 Annotation Processing + Rebuild |
| 5 | Entity `total` 字段映射失败 | 计算列无需插入/更新但需读取 | 实体中保留字段，不加 `@TableField` 约束，让 MyBatis-Plus 自动处理 null 值 |
| 6 | SQL `key` 关键字冲突 | MySQL 保留字用作列别名 | 使用反引号转义：\`key\` |
| 7 | IDEA 无法识别 Maven 项目 | 未添加 pom.xml | 在 Maven 面板手动添加 pom.xml |
